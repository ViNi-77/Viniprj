# contextgen v3 設計方針

- **作成日**: 2026年8月
- **位置づけ**: v2 系（AIナレッジ生成ツール）からの大型アップデート設計
- **起点**: 部署内レビュー（週報PPTXの抽出失敗報告）と、そこから判明した構造的課題

---

## 0. v3 で何が変わるか（結論）

v2 は「フォルダ → AIナレッジ（固定20ファイル）」の一方向ツールだった。
v3 は、**一度の抽出から三方向へ出力する**構造に変える。

```
                          ┌─→ ① AIナレッジ   （Copilotエージェント向け・v2の機能）
Boxフォルダ → [抽出] ─────┼─→ ② 人間向け読解キット（長大文書の分解・新規）
             （重い処理）  └─→ ③ 文書健康診断  （フォルダ全体の状態把握・新規）
```

抽出（最もコストが高い処理）とキャッシュは共通化し、出力だけを分岐させる。
既にプロファイル機構と差分キャッシュがあるため、構造的な追加は少ない。

**狙い**: 「AI導入の話」をしなくても価値が伝わる出口（②③）を持つことで、
AIに関心のない相手にも配布できるツールにする。

---

## 1. 柱1: 壊れないこと（部分的失敗の局所化）

### 1.1 判明した事実

2026年8月の監査で、**全抽出器が「一部の失敗＝全体の消失」構造**であることを実測で確認した。

| 壊した箇所 | 現状の結果 | 消失するもの |
|---|---|---|
| PowerPoint の図形1つ | status=error / 0文字 | タイトル・本文すべて |
| Excel の1シート | status=error / 0文字 | 無事な他シートすべて |
| PDF の1ページ | status=error / 0文字 | 正常ページの本文すべて |
| Word の表 | status=error / 0文字 | 本文パラグラフすべて |
| ZIP の1エントリ | status=error / 0文字 | 無事な同梱ファイルすべて |

PowerPoint の件は v2.2.0 で修正済み（`hasattr(shape,'table')` の ValueError）。
ただし**これは症状であって病因ではない**。病因は「抽出器全体を1つの
try/except で包み、例外時に空文字を返す」という共通構造にある。

### 1.2 なぜ重大か

- **静かに起きる**: 例外が出るわけでもエラーで止まるわけでもなく、
  「そのファイルには何も書いていなかった」のと区別がつかない
- **気づけない**: 実物で試して報告してくれる人がいなければ発覚しない
- **AIの回答品質に直結**: Copilot が「その資料は見当たりません」と答える原因になるが、
  原因究明のとっかかりが無い

### 1.3 v3 の設計

抽出を「構成単位（unit）」の集合として扱い、**単位ごとに独立して保護する**。

| 形式 | 構成単位 |
|---|---|
| PowerPoint | スライド → 図形 |
| Excel | ワークシート → 行 |
| Word | 段落 / 表 / セクション |
| PDF | ページ |
| ZIP | エントリ |

`ExtractResult` を拡張し、**部分抽出を一級の状態にする**。

```python
@dataclass
class ExtractResult:
    text: str
    status: str          # ok / partial / empty / needs_ocr / ... / error
    reason: str
    meta: dict
    units_total: int     # 例: 全12ページ
    units_ok: int        # 例: 10ページ抽出成功
    unit_failures: list  # [(単位の識別子, 失敗理由), ...]
```

- 新ステータス **`partial`** を追加（「取れたが完全ではない」を表現）
- レポートに「12ページ中10ページ抽出（p.4: 埋め込み画像の解析失敗）」と明示
- **抽出カバレッジ率**を文書単位・フォルダ単位で算出し、健康診断（柱3）に接続

### 1.4 実文書レグレッションコーパス

部署の実ファイル（匿名化）をテストデータ化し、次の変更で壊れないことを機械的に保証する。
現在のテストは合成データ中心で、**実世界の壊れ方**（埋め込み、方眼紙、
複雑な結合セル、スキャンPDF、旧形式）を再現できていない。

## 2. 柱2: 人間向け読解キット（v3 の目玉）

### 2.1 起点

実運用のレビューで出た声：

> 「長々しいドキュメントを『マニュアル』と称して量産する高齢の方がいて、
> それをBOXに詰めていくものだから、どーしよっかな…と思ってたとこでした。
> そのマニュアル、コイツで分解してくれるわ(笑)」

これは設計時に想定していなかった使われ方である。
**AIに読ませるためではなく、人間が読み解くために使われている。**

### 2.2 何を出すか

長大文書に対して人間が本当に知りたいのは以下であり、
そのほとんどは **LLM無しで機械的に抽出できる**（＝APIキー不要・データ持ち出しゼロという
本ツールの強みを維持できる）。

出力例：`_HUMAN_DIGEST/設備点検マニュアル.md`

```markdown
# 設備点検マニュアル.docx 読み解きキット

## 30秒でわかる
- 種別: Word / 約42ページ相当 / 18,432文字
- 文書内の最終更新記述: 2019年4月（**7年前**）
- 構成: 6章 / 見出し38個
- 読みにくさ: 1文あたり平均62文字（長文傾向）
- 抽出カバレッジ: 100%（全単位を読み取り済み）

## 目次（自動抽出）
1. 目的と適用範囲
   1.1 適用設備 …

## この文書が答えられそうな質問
- 適用設備は何か？（→ 1.1）
- 日常点検の頻度は？（→ 3.2）

## 気になる点
- ⚠ 「別紙2参照」とあるが、別紙2に該当する見出しが存在しない
- ⚠ 同一段落が3箇所に重複（重複検出機能を流用）
- ⚠ 同じ点検項目に「毎日」と「週1回」が併記（矛盾の可能性）

## Copilotに聞くときのコピペ用
（構造化済みテキスト。ここをコピーしてCopilotに貼れば、この文書について質問できます）
```

### 2.3 機械的に抽出できるもの（LLM不要）

| 項目 | 抽出方法 |
|---|---|
| 見出し階層 | docx スタイル / pptx スライドタイトル / PDF フォントサイズ / xlsx シート名 |
| 文書の古さ | 本文中の日付表現（「2019年4月版」「Rev.3」）＋ ファイル更新日 |
| 重複段落 | v2.1 の `dedupe.py`（bottom-k シングル + Jaccard）を文書内比較に流用 |
| 参照切れ | 「別紙N参照」「下記参照」等の参照表現と、対応する見出しの突合 |
| 数値の不整合候補 | 同一項目名に対する異なる数値・頻度表現の併記 |
| 読みにくさ指標 | 1文の平均長 / 見出し階層の深さ / 見出しなし連続行数 |
| 専門用語リスト | 頻出する固有名詞・型番の初出位置 |

### 2.4 フォルダ単位の読解キット

個別文書だけでなく、フォルダ全体に対しても出す（柱3と接続）。

```
このフォルダには38文書。うち12件が3年以上更新なし。
「マニュアル」を含む文書が9件あり、そのうち3件は内容が8割同一。
誰からも参照されていない孤立文書が5件（廃止候補）。
```

### 2.5 文書間リンクマップ（発展）

「別紙参照」「〜規定に基づく」等の記述から**文書間の参照関係**を抽出し、
- 孤立文書（誰からも参照されない）＝ 廃止候補
- ハブ文書（多数から参照される）＝ 最重要・優先メンテ対象
を可視化する。マニュアル群の整理に直接効く。

## 3. 柱3: 文書健康診断

柱1で得た**抽出カバレッジ**と、柱2で得た**構造・鮮度・重複**の情報を、
フォルダ単位のスコアとして1枚にまとめる。

| 指標 | 意味 |
|---|---|
| 抽出可能率 | AIが読める文書の割合（読めない＝AIから存在しないのと同じ） |
| 鮮度分布 | 最終更新からの経過期間のヒストグラム |
| 重複率 | 内容が重複するクラスタの割合 |
| 機密リスク | 機密スキャン検知件数（v2.1 機能） |
| OCR必要率 | テキスト層のないPDFの割合 |

**用途**: 「AIを導入する前に、まず自部署のナレッジを診断する」という導線。
経営層・情シスに見せる最初の1枚として機能する。

## 4. 権限の扱い（v3 では優先度を下げる）

当初 v3 の目玉候補として「権限スコープの継承・記録」を検討したが、
**現時点では不要**と判断した。理由は以下（部署内の確認による）。

- エージェント共有の制限は Microsoft 側の制約ではなく、**自社セキュリティルール**による
- Copilot には2種類あり、**Copilot Studio** は共有前提で権限の細かい設定が可能
- **エージェントビルダー**は、機密情報をナレッジ登録して共有すると
  本来アクセス権のない人が参照できるリスクがあるため、自社では共有不可としている
- そもそも「エージェントビルダーで機密を含むエージェントを作らない」運用で回避できる

したがって v3 では実装しない。ただし、
**Copilot Studio での共有運用へ移行する場合には再浮上する論点**として記録しておく。
（特許のクレーム候補としては引き続き有効。`PATENT_CANDIDATES.md` 参照）

## 5. 実装順序（案）

| 順 | 内容 | 規模 | 理由 |
|---|---|---|---|
| 1 | `ExtractResult` の unit 拡張 + `partial` ステータス | 中 | 他の全機能の土台になる |
| 2 | 全抽出器の部分的失敗の局所化 | 中 | 信頼性の回復。最優先の実害 |
| 3 | 実文書レグレッションコーパス | 小 | 2を保証するために必要 |
| 4 | 人間向け読解キット（個別文書） | 大 | v3 の目玉 |
| 5 | 文書健康診断（フォルダ単位） | 中 | 4の集計として自然に作れる |
| 6 | 文書間リンクマップ | 中 | 4の発展。効果は大きいが後回し可 |
