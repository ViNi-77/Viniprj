# AI 開発指示書（草案）

企画書 2 章・9 章を、ローカル環境で AI エージェントに委任する際の運用規則に落とした。

## 1. 役割
| 役割 | 担当（企画書の想定） | 本リポジトリでの作業 |
|---|---|---|
| 実装担当 | GPT-6 Astra | Issue 単位で実装 → `python -m pytest` → `python scripts/run_e2e.py` → 実ファイル確認 → コミット |
| レビュー担当 | Fable 5.1 | 差分レビュー（下記観点）→ 指摘は Issue またはレビューコメント。要件・コード・試験結果の不一致を指摘 |
| 共通 | 両者 | 一方の変更を他方が必ずレビューする。自己承認しない |

モデル名は利用予定名称。実際の利用可否・権限・API 仕様は利用環境側で確認する。

## 2. 禁止事項
- 要件外機能の独断追加（追加したい場合は Issue を立てて合意を得る）。
- 実データ・固有名詞・社内テンプレートのコードへの固定。サンプルは架空データのみ。
- 外部サービスへのファイル送信。外部 URL の画像取得。
- 試験の削除・スキップによる「緑化」。
- 設定値のハードコード（`config/*.json` を使う）。
- 未対応要素での例外停止（警告 + 代替処理にする）。

## 3. 変更手順
1. `docs/01_要件定義書.md` と `03_変換マッピング仕様書.md` の該当箇所を確認し、無ければ先に追記する。
2. 小さな縦切りで実装する（例: 「HTML の `<dl>` 対応」= parser + renderer + generator + test）。
3. 日本語注釈を付ける（何を・なぜ）。
4. `python -m pytest` と `python scripts/run_e2e.py` を通す。
5. 生成物を実ファイルで確認する（Web は file:// で開く、PPTX は PowerPoint で開く）。
6. `docs/99_意思決定ログ.md` に判断を残す。
7. コミットメッセージは「何を・なぜ」。試験結果の版（`docs/試験結果.md`）を同時に更新する。

## 4. レビュー観点
- 要件との対応: 追加・変更が要件定義書のどの項目に対応するか。
- フォールバック: 失敗時に停止せず警告を出しているか。警告コードは一意で説明的か。
- 決定性: 同じ入力から同じ JSON が出るか（ID 生成、並び順）。
- 単位・座標: pt 統一。EMU/px 変換の取り違えが無いか。
- 往復: PPTX → JSON → PPTX → JSON で題名・枚数・要素種別が保たれるか。
- 品質: 文字切れ・重なり・画像比率の検査が新要素にも効くか。
- セキュリティ: 外部通信・パス操作（保存名の正規化）・HTML エスケープ。

## 5. 成果物の命名
- 出力ファイル: `<資料名>_<YYYYMMDD_HHMMSS>.<拡張子>`（`output/`）。
- プロジェクト: `projects/<名前>.json`。
- 文書: `docs/NN_<名称>.md`（NN は 2 桁の並び）。試験結果は `docs/試験結果.md` を上書き。

## 6. 将来の AI 連携の差し込み点
初期版はすべて決定的処理。企画書 3.1 の「AI は構造理解・分類・要約・レイアウト候補選択を担当」は、次の関数を差し替える形で追加する。
- `html_parser._find_slide_containers` / `_classify_layout`: スライド境界と layout の分類。
- `layout.layout_slide`: レイアウト候補の選択（座標計算自体は残す）。
- 出力は必ず `validate.validate_and_repair` を通し、JSON Schema で制御する。
