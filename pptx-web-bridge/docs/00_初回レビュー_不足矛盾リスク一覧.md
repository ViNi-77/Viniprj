# 初回レビュー: 企画書に対する不足・矛盾・実装上の高リスク一覧

企画書「PowerPoint・Web図解 双方向変換アプリ」（企画初版 2026年9月9日）を読み、実装開始前に整理した。
企画書 9 章「最初に不足・矛盾・実装上の高リスクを一覧化する」への回答。

## 1. 不足（渡された資料に無いもの）

| # | 項目 | 影響 | 本実装での扱い |
|---|---|---|---|
| 1 | 企画書 5 章の必須2〜9・推奨10〜13 の書類が添付されていない（基本設計基準書、専用要件定義書、JSON 仕様、マッピング仕様、サンプル PPTX/HTML、テンプレート規則、受入試験仕様、AI 指示書 等） | 設計の根拠を企画書のみから起こす必要がある | 企画書の記述から **草案** を `docs/` に作成した。正式版が届いた時点で差分レビューする（各文書の冒頭に「草案」と明記） |
| 2 | 10 章の参照資料（`アプリ基本設計基準書.md`、`teams_netta_infographic 1.pptx`、`基礎資料①②`、`生成AI利用ガイドライン` 等）が無い | 友松スタイルの設計基準、配色、機密表示ルールを確認できない | 企画書 5 章に列挙された原則（ハードコード禁止、動的解析、D&D、フォールバック、日本語注釈、デバッグ、品質保証）を設計方針として採用。配色・機密表示は架空値で `config/templates.json` に外出し |
| 3 | 正式テンプレート・ブランド規則（6.2 で「この場で確定」とされているが未確定） | 出力の色・フォント・フッター・機密表示が決められない | 「プレーン」と「架空サンプル」の 2 テンプレートを設定ファイルで用意。正式版は JSON を追加するだけで差し替え可能 |
| 4 | 変換品質の合格基準（許容差の数値） | 自動検査のしきい値を決められない | `config/app_config.json` の `quality.*` に暫定値（文字あふれ 115%、重なり 15%、画像比率 3%）を置き、設定で変更可能にした |
| 5 | 想定利用者の具体像と利用頻度 | UI の作り込み度合いを判断できない | 「非エンジニアがブラウザで投入→プレビュー→出力」を最小要件とし、3 ペイン構成の素の HTML/JS で実装 |
| 6 | 成果物の権利帰属・OSS 利用条件の確認表 | 依存ライブラリの採否根拠が無い | `docs/07_既知課題と確認事項.md` に依存ライブラリとライセンスを列挙し、確認待ちとした |
| 7 | AI エージェント（GPT-6 Astra / Fable 5.1）の実際の利用可否・API 仕様 | 役割分担の実行方法が決まらない | 本リポジトリは特定モデルへ依存しない構造にした。AI 連携は初期版の対象外（企画書 3.1 の「AI は構造理解を担当」は将来拡張点として `docs/05_AI開発指示書.md` に記載） |

## 2. 矛盾・曖昧な点

| # | 記述 | 問題 | 採った解釈 |
|---|---|---|---|
| 1 | 3 章「PPTX 出力は PptxGenJS を第一候補、python-pptx を補助候補」 vs 「ローカル API は Python + FastAPI」 | JS 生成器を使うと Node ランタイムが必須になり、起動と配布が二重化する | **python-pptx を主生成器に採用**。PptxGenJS は Node 依存が増えるため初期版では見送り（意思決定ログ #2） |
| 2 | 1.2「Web図解から再編集可能な PowerPoint」 vs 4 章「PPTX 出力: 編集性優先／見た目優先／ハイブリッド」 | 見た目優先は再編集できない | 3 モードを用意し、見た目優先は画像貼付＋代替テキストにテキストを保持する形とした。既定は編集性優先 |
| 3 | 3 章「HTML 入力: Playwright による DOM・Computed Style・画像取得」 vs 1.3 非目標「任意 Web サイトの無制限クロール」 | どこまでブラウザ実行するかが曖昧 | 構造解析は BeautifulSoup（静的 DOM）で行い、Playwright は**自作 HTML の画像化**のみに使用。外部 URL の画像は取得せず警告 |
| 4 | 4 章 MVP「16:9」 vs 実資料には 4:3 が混在し得る | 4:3 の扱いが未定義 | 4:3 も読み込み、比率を保持したまま処理し警告を出す（`ASPECT_NOT_16_9`） |
| 5 | 3 章「配布候補: shell 起動、アプリバンドル、社内 Web 移行」 vs 10 章「PyInstaller 要件」 | 配布方式の決定者・時期が不明 | shell 起動スクリプトを実装し、比較表を `docs/06_起動方式比較.md` に置いた。最終決定は Windows 実機での検証後 |
| 6 | 2.1「GPT-6 Astra が操作・実装」「Fable 5.1 がレビュー」 vs 9 章「実装担当とレビュー担当を分離」 | 本セッションは 1 エージェントで実装している | 実装→自動試験→再読込確認を各変更ごとに行い、レビュー観点を `docs/05_AI開発指示書.md` に明文化した。相互レビューは別担当で実施する |

## 3. 実装上の高リスク

| # | リスク | 発生箇所 | 対策（実装済み） | 残リスク |
|---|---|---|---|---|
| 1 | フォント計測が無いため文字あふれを正確に判定できない | 自動レイアウト、品質検査 | 全角＝サイズ幅／半角＝0.55 倍の近似で行数を推定し、余裕を持たせて警告。しきい値は設定化 | 実フォントとの差。PowerPoint 実機で開いて確認する必要がある |
| 2 | PPTX の書式継承（レイアウト・マスター由来の色・サイズ・箇条書き）を取りこぼす | PPTX 解析 | 取れない値は役割（title/body）既定値で描画。本文プレースホルダは箇条書き既定 | テーマ色（scheme color）は未解決で既定色になる |
| 3 | SmartArt・グラフ・動画は再現不能 | PPTX 解析 | SmartArt は文字列を箇条書きへ退避、グラフは枠＋題名、いずれも警告。停止しない | 見た目は失われる（企画書 1.3 の非目標どおり） |
| 4 | 見た目優先モードは Playwright/Chromium に依存 | PPTX 生成 | 未導入なら編集性優先へ自動フォールバックし警告 | 初回セットアップで約 150MB のブラウザ導入が要る |
| 5 | 任意 HTML の構造は無限に多様 | HTML 解析 | section／見出し／class 名（card, grid）の 3 段階で境界判定。未知タグは中身をたどり文字を失わない | 企画書のサンプル HTML が無いため、実資料での検証が未了 |
| 6 | CI 環境には LibreOffice Impress が無く、生成 PPTX の画面確認ができない | 試験 | python-pptx による再読込・XML 妥当性・往復一致で代替 | PowerPoint 実機での開閲・編集確認は Windows 実機で行う（受入条件「生成 PPTX が PowerPoint で開き編集できる」は未確認） |
| 7 | 機密情報の外部送信 | 全体 | すべてローカル処理。外部 URL へアクセスするコードは無い（画像も取得しない） | ブラウザ自動オープン以外に外部通信は無い |
| 8 | 画像を JSON に base64 で内包するため、大きな資料では JSON が肥大化する | 保存 | アップロード上限（50MB）を設定化。Web 一式出力時は別ファイルへ分離 | 100 枚超の画像資料では保存・プレビューが遅くなる |

## 4. 企画書の記載どおり「追加しなかった」もの

- 認証、データベース、共同編集、履歴マージ（1.3 非目標）
- 任意 Web サイトのクロール、ログイン後ページ（4 章対象外）
- SmartArt・動画・音声・マクロ・3D・アニメーションの再現（4 章対象外）
- AI モデルの呼び出し（初期版はすべて決定的処理。企画書 3.1 の AI 担当部分は将来の差し込み点として設計）

## 5. 追加資料の受領後レビュー（同日 第2版）

受領: QC事例質疑応答練習アプリ 要件定義書、アプリケーション基本設計基準書（2 版）、匿名化スライド仕様書、模擬PPTX生成指示書、テンプレート参考画像 3 枚（表紙・中身・最終ページ）、指示「文字は画像ではなくテキストシェイプとして座標・サイズを数値化して落とし込むこと」。

### 5.1 解消した不足
| # | 項目 | 対応 |
|---|---|---|
| 2 | サンプル PPTX | `mock-pptx/` に匿名化 12 枚を生成器付きで用意（仕様書・指示書準拠、自動検査・検査記録・プレビュー PDF 同梱） |
| 3 | テンプレート・ブランド規則 | `config/templates.json` の `corporate_standard` に表紙・中身・最終ページの部品定義（A色 #001A72 等の配色、メイリオ 32pt/21pt） |
| 4 | 文字のテキストシェイプ化 | 全モードで文字はテキストシェイプ（見た目優先のみ画像 + 代替テキスト）。`要素判別レポート` で 種別 / x,y,w,h / pt を数値表示 |

### 5.2 新たな矛盾・判断
| # | 記述 | 問題 | 採った解釈 |
|---|---|---|---|
| 1 | 模擬PPTX生成指示書 4 章「第一候補 PptxGenJS」 | アプリ本体は Python。Node 追加は再現手順の二重化 | 代替候補の python-pptx を採用（指示書が代替を許容）。理由は `mock-pptx/README.md` |
| 2 | 匿名化仕様書「実在ロゴ・正式テンプレートを複製しない」 vs 参考画像のロゴ入りテンプレート提供 | 模擬資料とアプリのテンプレートで要求が異なる | 模擬 12 枚は Generic Corporate Blue（ロゴ無し）。アプリのテンプレートは参考画像から切り出した暫定ロゴを `config/template_assets/` に置き、正式素材へ差し替える前提 |
| 3 | 基本設計基準書 2.3「GCP プロジェクト ID 等の既定値をハードコード可」 | 本アプリは AI 接続を持たない | 該当なし。将来 AI を接続する場合は `models.json` 方式（4.4）で外出しする |
| 4 | 基本設計基準書 3.1「Glassmorphism / Google Fonts / FontAwesome」 | 外部フォント・CDN 依存はローカル完結と衝突 | 配色・可読性は踏襲し、外部 CDN は使わない（オフライン動作を優先）。必要なら同梱フォントで対応 |
| 5 | 指示書 12 章「実装前に採用技術等のみを提示」 | 本セッションは自律実行 | 提示内容を `mock-pptx/README.md` と本レビューに記載した上で最小実装を実施 |
| 6 | 「AI が画像と文字を自動判別」 | 画像内に焼き込まれた文字（写真化された図など）は OCR 無しでは文字化できない | PPTX/HTML 上でテキストとして存在する文字は 100% テキストシェイプ化。画像内文字は将来の Vision AI（基準書 4.1）対象として既知課題に記載 |
| 7 | 参考画像の解像度（600〜800px） | ロゴ切り出しが粗い | 暫定資産として同梱。正式ベクターデータで差し替え（同名ファイル） |
