# ループエンジニアリング運用（Issue 駆動の反復開発）

「小さく作り、毎回検査し、記録を残し、次の 1 手を Issue で決める」を機械的に回す。人（ビニ）は Issue の優先順位と受入判断だけを行い、実装・検査・記録は AI と CI が担う。

## 1. ループの 1 周（1 Issue = 1 周）
```
① Issue を選ぶ（受入条件が書かれているもの。無ければ先に書く）
② ブランチ: 作業は claude/... ブランチ、または Issue 番号付きブランチ
③ 実装（小さな縦切り。要件外は別 Issue へ）
④ 検査:  python scripts/loop.py --issue <番号>     ← 単体・API → 模擬PPTX → E2E を一括
         実装中は python scripts/loop.py --quick で高速反復
⑤ 実ファイル確認: output/e2e/ の Web と PPTX を開く（実機は PowerPoint、CI は再読込）
⑥ レビュー: 実装担当と別の担当が docs/05 4 章の観点で差分を読む（GPT-6 Astra ⇄ Fable 5.1）
⑦ 記録: docs/ループ実行記録.md（自動追記）、docs/99_意思決定ログ.md（判断があれば）
⑧ コミット → push → CI（.github/workflows/loop.yml）が同じ検査を再実行 → PR に Closes #番号
⑨ 受入: 人が受入条件を確認して Issue を閉じる。次の Issue へ
```
不合格なら ③ に戻る。3 周しても合格しない場合は Issue を分割するか、既知課題（docs/07）へ移して止める。

## 2. 役割
| 役割 | 担当 | やること |
|---|---|---|
| 依頼者 | ビニ | Issue の優先順位、受入判断、正式素材・ブランド規則の提供 |
| 実装担当 | GPT-6 Astra（想定） | ③④⑤⑦⑧ |
| レビュー担当 | Fable 5.1（想定） | ⑥、仕様書との不一致指摘、次 Issue の提案 |
| CI | GitHub Actions | ⑧ の再検査、成果物の保存 |
モデルが 1 つしか使えない場合も、実装とレビューを別セッションに分けて自己レビューを避ける。

## 3. Issue の書き方
- テンプレート `.github/ISSUE_TEMPLATE/task.md` を使う。**受入条件**と**検査方法**が無い Issue は着手しない。
- 大きさの目安: 1 周が 1〜2 時間以内。超えるなら分割。
- 種類の目安（ラベル）: `enhancement`（機能）、`bug`（不具合）、`documentation`（文書）、`question`（人の判断待ち）。

## 4. 検査の中身（scripts/loop.py）
| 段階 | コマンド | 合格条件 |
|---|---|---|
| 単体・API | `pytest tests` | 全件合格 |
| 模擬 12 枚 | `mock-pptx/src/generate_mock_pptx.py` → `pytest mock-pptx/tests` → `validate_mock_pptx.py` | 全件合格、警告 0、品質検査 0 |
| 往復 E2E | `scripts/run_e2e.py` | 全項目合格（docs/試験結果.md を更新） |
| 記録 | docs/ループ実行記録.md | 1 行追記（日時・コミット・Issue・結果）。コミット列は**検査時点の HEAD（実装コミットの親）**。実装コミットはその直後の履歴を見る |

## 4.1 検査結果でコミットを止める書き方
`scripts/loop.py` は不合格で終了コード 1 を返す。シェルで `&&` により後続のコミットを止めるときは、`grep` などを挟むと終了コードが上書きされるため、必ず `set -o pipefail` を付けるか、`python scripts/loop.py --issue N && git commit ...` のように直接つなぐ。
（2026-09-09 に grep 経由で不合格のままプッシュした事例あり。次のコミットで修正）

## 5. 止めるべきサイン
- 同じ Issue で 3 周以上不合格 → 分割または既知課題化
- 検査を緩めたくなる（しきい値変更・テスト削除）→ 禁止。別 Issue で合意してから
- 要件外の機能を足したくなる → 新しい Issue にして今の周では触らない
