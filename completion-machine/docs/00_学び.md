# 00 学び — このPoCを作るときに守った「プロダクト作り」の原則

外部の講座で学んだことを、自分の言葉で書き直したもの。講座の文章は引用しない。
各行の右端は、このPoCでどう実行したかを指す。

## 1. 何を作るかを決めるとき

| 原則 | このPoCでの実行 |
|---|---|
| 課題仮説と解決仮説を、一文ずつ分けて書く | `01_要件定義.md` の冒頭に2文で置いた |
| 業務を分解して、無意識の手順を言葉にする。その後で類似サービスを調べる | 研修の「補完機」「3つの壁」「手紙の中身」を工程8つに分解した |
| 既存ツールで届かない部分だけを作る | スライドと動画では「自分で押して確かめる」ができない。それだけを作った |
| 最小限は「自分で恥ずかしいくらい」。コードなしで検証できないかを先に考える | 1機械・8工程・単体HTML。研修で見せて反応を見るまでが範囲 |

## 2. 作り方

| 原則 | このPoCでの実行 |
|---|---|
| 一番怪しいところを、使い捨ての場所で単独に確かめる | ①日本語がSVGで崩れないか ②ボタン列を置いても検査が通るか ③`seek(t)` が決定論か、を本体の前に確かめた |
| 完成形の絵（模範解答）を先に作る | `02_設計.md` に画面の文字絵と部品表を書いてから幾何を書いた |
| 全体地図と詳細地図を同時に見せる。2秒で要点が分かる | 左に工程列、中央に機械、下に一文のビッグアイデア |
| ブレてはいけない部分（計算・順序・時間）はコードに任せる | 数値・順序・時刻は `js/model.js` の純粋関数が決める |
| 正しい情報の置き場所を1か所にする | 数値は `js/data.js` だけ。出典は `03_数値の根拠.md` と一致させる |
| 出力がおかしいときは手で直さず、渡すもの（設計・ルール）を直す | 検査で落ちたら設計表を直してから再生成する |
| 図で認知の負担を下げる。一図一メッセージ | ビッグアイデアは一文。それで言えないものは入れない |

## 3. 終わり方

| 原則 | このPoCでの実行 |
|---|---|
| 合格基準を先に言葉にし、作った本人以外が判定する | `04_受入試験.md` を先に書き、`scripts/ui_smoke.py` が判定する。最後に別の目で通しで触る |
| 作り手以外の実ユーザーに触らせ、「また使いたいか」を聞く | 完成後に1人に触ってもらう。研修本番での計測は次の段階 |
| 語りは「結論 → 困りごとの情景 → 放置した場合 → 変化後の情景 → お願い」 | README の冒頭と `05_映像設計.md` の台本をこの順にした |
| こまめに commit し、push の前に点検する | 工程ごとに commit。push 前に機密・外部URL・講座原文がないことを確認 |

## 4. 言葉の選び方（受講者向け）

- 最初は専門用語を出さない。「トークン」「確率分布」は画面に出さず、「手紙」「机」「一語」で通す。
- 「AIが疲れる」「AIが覚えている」のような、仕組みと違う言い方をしない。毎回まっさらで、手紙が重くなっているだけ。
- 横文字を並べない。一つずつ説明する。
